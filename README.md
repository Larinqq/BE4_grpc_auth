# BE4_grpc_auth

## Описание проекта

## Авторы: Ganisrum (Никита Ларьков) Ahaidewi (Евгений Самаров)

Групповой проект: магазин бытовой техники с вынесенным сервисом авторизации на gRPC. Реализована полноценная схема аутентификации и авторизации пользователей с разделением на отдельное приложение и собственное хранилище данных.

## Архитектура
  - Основное приложение — REST API магазина (Spring Boot), все защищённые ручки проходят аутентификацию через внешний сервис.
  - Сервис авторизации — отдельное приложение с собственной базой PostgreSQL (отдельная БД, не таблица), взаимодействие с остальной системой только по gRPC (работает поверх HTTP/2).
  - Настроен IoC-контейнер (Spring DI): реализации прокидываются через интерфейсы.

## Сервис авторизации (gRPC)
Описан .proto-файл с контрактами и реализованы методы:
  - Создание пользователя (почта, имя, фамилия, телефон, пароль) → возвращает подписанный JWT.
  - Аутентификация по паре логин-пароль → возвращает токен.
  - Смена пароля пользователя.
  - Восстановление пароля — заглушка отправки на почту (вывод пароля в консоль сервиса).
  - Безопасность паролей: хранятся в хэшированном виде с солью, без устаревших и уязвимых md5/sha1.

## Интеграция с магазином

  - Добавлены публичные эндпоинты без аутентификации: /register, /auth, /reset — ходят в сервис авторизации для создания/проверки данных.
  - Авторизация всех API-ручек реализована через самописный атрибут авторизации, логика обработки которого вынесена в middleware.
  - Middleware по gRPC обращается в сервис авторизации для валидации токена: валиден → запрос идёт в обработчик, иначе → 401.
  - JWT передаётся в заголовке Authorization.

Стек: Spring Boot, Spring Security, gRPC + Protobuf, PostgreSQL, JWT, DI/IoC.

## Результат
Построена распределённая система с выделенным сервисом аутентификации: единая точка проверки токенов для всех API магазина, безопасное хранение паролей и слабая связанность сервисов за счёт gRPC-контрактов.
